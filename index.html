Rebuilt from Tarun's 15-day notes into a searchable methodology. Each entry carries a plain-spoken relevance read — rising, still common, declining, or mostly historical today, based on how modern frameworks, browsers, and cloud defaults have actually moved the needle since these notes were first written — plus field notes linking to real disclosed reports. Use the search/filter layer below to jump straight to what's worth your time, or just read the chapters top to bottom.

The mental model behind every chapter: INPUT → MANIPULATE → OBSERVE → BOUNDARY → IMPACT. Find where the application accepts something from you (a field, a header, a token, an ID). Change it in a way the developer probably didn't expect. Watch exactly what comes back — an error, a status change, a different length. Name the security boundary that should have stopped you (authentication, authorization, encoding, rate limiting…). Only then ask what real-world impact crossing that boundary gives you. Every entry below is one pass through that loop — and every chapter states the invariant that, if it ever breaks, means the boundary failed.

Chapter 0 — Recon & Domain Hygiene

Before you ever touch a login form, the domain itself is an attack surface. This chapter is about everything you can learn and break without an account: who the domain trusts, what it has forgotten about, and what it's quietly leaking. Run it once at the start of every engagement — half of these findings cost nothing but a few minutes and a browser tab.

Chapter invariant: Nothing outside the application's control boundary — an old subdomain, a social handle, an open port — should be able to speak for the domain or expose its internals.

Subdomain takeover Infra

Still common

Still found constantly — new SaaS integrations create new dangling-CNAME candidates faster than teams can track them.

A subdomain's DNS record (CNAME) still points at a third-party service (S3 bucket, Heroku app, GitHub Pages) that the company deleted or never claimed. The hostname resolves, but the service behind it doesn't exist — so anyone can claim that service and serve content under the company's own domain.

Walkthrough

  1. Enumerate subdomains with amass or subfinder.
  2. For each one, check where its CNAME points (dig CNAME sub.target.com).
  3. If it points at a provider (S3, Azure, Heroku, GitHub Pages, Fastly…) and that provider says the resource doesn't exist, it's dangling.
  4. Register the same resource name on that provider and point your own content at it — a working page under the company's subdomain is your proof.

Impact

A full takeover of trust — phishing pages, cookie theft via subdomain-scoped cookies, or bypassing CSP/CORS rules that whitelist the parent domain.

Invariant: Every DNS record that points outward must point at something the company still owns.

Fix

Remove the DNS record the moment the underlying resource is decommissioned.

Broken link hijacking Infra

Declining

Still exists, but most programs treat it as low/informative since impact is limited to impersonation, not data access.

The company's own site links out to a social media account, old partner site, or App Store listing that no longer exists under that name.

Walkthrough

  1. Walk the footer, about page, and any transactional emails for outbound social/partner links.
  2. Click each one — if it resolves to "page not found" or "account doesn't exist" rather than a real profile, it's up for grabs.
  3. Register the account under the company's name/handle on that platform as proof of concept.

Impact

Impersonation — you can now post "official" content, phishing links, or support replies that look legitimate.

Invariant: Every link the company publishes about itself should point at an account the company still controls.

Fix

Audit outbound links on a schedule; remove ones to abandoned accounts.

DMARC / SPF missing or misconfigured Infra

Declining

Very commonly missing, but most bounty programs now mark it informative/won't-fix unless chained into a real phishing PoC.

SPF and DMARC are DNS records that tell receiving mail servers which servers are allowed to send mail "from" the domain, and what to do if a message fails that check.

Walkthrough

  1. Check mxtoolbox.com and kitterman.com/spf/validate.html against the domain.
  2. Confirm an SPF record exists and lists the real sending infrastructure.
  3. Confirm DMARC exists with p=quarantine or p=reject — p=none means violations are only reported, never blocked.

Impact

Anyone can send email that appears to come from the company's own domain — textbook phishing.

Invariant: Mail claiming to be from the domain must be verifiably from the domain, or rejected.

Fix

Publish SPF covering real senders; set DMARC to quarantine/reject once the SPF/DKIM rollout is confirmed clean.

WAF bypass via origin IP disclosure Infra

Still common

Cloudflare/Fastly 'orange-to-orange' and strict-origin-pull features exist now, but most sites still don't enable them — origin IP leaks remain routine.

A site sits behind Cloudflare or a similar WAF, but the real server's IP address is still discoverable — through old DNS history, a misconfigured subdomain, or scan databases — and still answers requests directly.

Walkthrough

  1. Check the firewall in use with wafw00f.
  2. Search censys.io or shodan.io for certificates/banners matching the target to find candidate origin IPs.
  3. Send a request directly to that IP with the Host header set to the real domain.
  4. If you get the real site back, the WAF is being routed around entirely.

Impact

Every protection the WAF provides — rate limiting, payload filtering, DDoS mitigation — is void; you're talking straight to the origin.

Invariant: The origin server should only accept traffic that has passed through the WAF.

Fix

Firewall the origin to only accept connections from the WAF's IP ranges.

Directory listing & exposed config/secrets Infra

Still common

CI/CD pushing build artifacts and .env files to public buckets is, if anything, more common now than a few years ago.

Web servers sometimes expose their raw file listing, or leave backup/config files sitting in a publicly reachable path.

Walkthrough

  1. Run ffuf/dirsearch/gobuster against the target with a content-discovery wordlist.
  2. Flag any 200 response on backup (.bak, .zip, .old), config (.env, .yml, web.config), or listing-style paths.
  3. Open the file and check what it actually contains — this is where the finding either dies or becomes critical.

Impact

Ranges from "minor info leak" to "full database credentials" depending on what's in the file.

Invariant: Nothing beyond the intended static assets should be servable from a web root.

Fix

Disable directory listing at the webserver level; keep secrets out of the web root entirely.

Debug / verbose error pages Infra

Still common

Still a frequent finding, especially on staging/internal environments accidentally left reachable.

Some environments ship with debug mode or a verbose error handler left on, which dumps stack traces, internal IPs, or framework details to anyone who triggers an error.

Walkthrough

  1. Try common debug paths: /debug, /actuator, /_profiler, /trace.
  2. If none exist, force an error with malformed input and read what comes back in the response.
  3. Collect anything that looks like an internal hostname, IP range, or dependency version.

Impact

Internal network topology becomes a roadmap for further attacks (SSRF targets, version-specific exploits).

Invariant: An error shown to the public should never contain information only useful to someone attacking the system.

Fix

Turn off debug/verbose mode in production; return generic error pages.

Port scanning & exposed services Infra

Still common

Cloud misconfiguration (open DB ports, exposed Elastic/Redis/Jenkins) is one of the most consistent bug classes in recent years.

Beyond 80/443, in-scope hosts sometimes run services (databases, admin panels, SSH, RDP) that were never meant to be internet-facing.

Walkthrough

  1. Run nmap -sV against in-scope IPs.
  2. Flag anything that isn't HTTP/HTTPS and doesn't need to be public.
  3. Check if the exposed service itself has a login — this is where recon turns into the next finding.

Impact

Direct access to infrastructure that was supposed to sit behind a firewall.

Invariant: Only services genuinely meant for public use should be reachable from the internet.

Fix

Firewall internal services; only expose what the product requires.

Default / weak credentials on exposed services Infra

Still common

As common as ever on self-hosted/third-party admin tools bolted onto a target's infrastructure.

Admin panels, FTP servers, and management consoles are sometimes left with vendor-default or trivially weak logins.

Walkthrough

  1. Try common defaults (admin/admin, anonymous/anonymous) on any login you found during port scanning or directory discovery.
  2. Check vendor documentation for that product's documented default credentials.

Impact

Full administrative access to whatever the panel controls.

Invariant: Every credential that guards something sensitive must have been deliberately set, not inherited from a default.

Fix

Force credential rotation on first login for any admin-facing tool.

Chapter 1 — Signup & Registration

This is the first input surface a user — or an attacker — ever touches. Everything here follows the same question: does creating an account actually require what the app claims it requires? A verification email that isn't checked, a password policy that isn't enforced, or a captcha that only runs once are all versions of the same failure — the client-visible promise and the server-side reality have drifted apart.

Chapter invariant: Creating an account must require proof of ownership over the email/phone used, a password strong enough to resist guessing, and a human (not a script) behind each submission.

Weak registration implementation Auth

Declining

Modern auth frameworks (Auth0, Cognito, Firebase Auth, Devise, etc.) handle this correctly by default; still shows up in hand-rolled registration flows.

Account-verification flows sometimes don't actually verify anything — the account is usable before the link is clicked, or the link itself is predictable or sent over plain HTTP.

Walkthrough

  1. Register a new account normally.
  2. Open the verification email, right-click → copy link rather than clicking it, so you can inspect it first.
  3. Check the link is HTTPS, and see whether the account was already fully functional before you ever opened that email.
  4. Paste the link in a fresh tab and confirm what actually changes when it's visited.

Impact

An attacker-created account (using someone else's email) can be used immediately, with the real owner never confirming anything.

Invariant: No sensitive capability should be available to an account until its contact method is proven to belong to that person.

Fix

Gate all sensitive actions behind a confirmed-email flag, not just "account exists."

No / weak password policy Auth

Declining

Most frameworks now enforce a minimum policy by default — still found in custom or older codebases, but no longer the easy win it once was.

Weak policy is as simple as the server accepting a one-character or dictionary-common password.

Walkthrough

  1. Go to signup, set the password field to something trivial like "1" or "password".
  2. Submit and see whether the account is created.

Impact

Every account on the platform inherits the brute-forceability of its weakest possible password.

Invariant: A password must meet a minimum strength bar enforced server-side, not just suggested client-side.

Fix

Enforce length + complexity server-side; check against a common-password blocklist.

HTML / email injection in profile fields Injection

Declining

Modern templating engines auto-escape by default, so this now mostly needs a developer to have explicitly used a 'raw'/'unsafe' render helper.

If the name fields a user fills in get embedded, unescaped, into a transactional email (a welcome note, a reset email), you can inject markup into mail sent from the company's own address.

Walkthrough

  1. During signup, put a payload like into the first-name or last-name field.
  2. Trigger any system email — a password reset, an invite, a receipt.
  3. Check whether the image actually loads inside the received email (confirms raw HTML rendering, not escaping).

Impact

Phishing mail that looks 100% legitimate because it genuinely comes from the company's mail server — attackers can reformat or add links to an otherwise real email.

Invariant: User-supplied text must be HTML-escaped before it's placed inside any email template.

Fix

Escape/sanitize all user input before interpolating it into HTML email bodies.

Captcha bypass — token reuse Logic

Declining

reCAPTCHA v3/hCaptcha score-based flows and proper server-side single-use enforcement have closed the easy version of this; still found on custom or older captcha integrations.

A captcha is only meaningful if it's checked once, tied to the single submission it was solved for.

Walkthrough

  1. Solve the captcha once and capture the request in Burp.
  2. Send the same request to Intruder with a null-payload attack (same request, repeated) 100 times.
  3. If every attempt returns success, the captcha token is being accepted repeatedly instead of being invalidated after first use.

Impact

Automation (credential stuffing, mass fake signups, OTP brute force) proceeds exactly as if there were no captcha at all.

Invariant: A solved captcha token must be consumed — valid for exactly one request.

Fix

Invalidate the captcha token server-side the moment it's used.

Captcha bypass — parameter removal Logic

Still common

Still one of the first things worth trying — a surprising number of implementations only validate the captcha if the field is present at all.

Some implementations only validate the captcha if its parameter is present at all — simply not sending it skips the check.

Walkthrough

  1. Fill the form including the captcha, intercept the request in Burp.
  2. Delete the captcha token/parameter entirely from the request body.
  3. Forward it and see whether the server still processes the submission.

Impact

Same as above — full automation of whatever the captcha was meant to gate.

Invariant: Absence of the captcha field must be treated as a failed check, not a skipped one.

Fix

Reject the request server-side whenever the expected captcha parameter is missing.

No rate limit on signup / OTP / SMS / email verification Logic

Still common

Consistently one of the most-reported classes on every bug bounty platform, pentest-up to today.

Any endpoint that sends a message (SMS, email) or checks a short numeric code (OTP) is a target for raw repetition — if nothing throttles it, it can be abused directly or brute-forced.

Walkthrough

  1. Capture the target request (signup, OTP-verify, SMS-trigger, email-verify, invite-user, forgot-password).
  2. Send it to Burp Intruder; for flooding, use a null-payload attack with ~100 repeats; for OTP brute force, use a numeric payload covering the code space.
  3. Watch for: the victim receiving a flood of messages, or — for OTP — one response differing in length/status at the correct code.

Impact

Either a denial-of-service/cost attack on the company's messaging budget, or in the OTP case, a full account takeover once the correct code is found.

Invariant: Any endpoint that costs money to call (SMS/email) or gates an account (OTP) must be rate-limited per account and per IP.

Fix

Add IP- and account-scoped rate limiting, with a backoff that increases on repeated failures.

OAuth account takeover via unverified email change Auth

Still common

Still a live class — OAuth/email-linking edge cases are exactly the kind of logic gap that survives multiple rounds of 'normal' security review.

If a user can sign up via Google/Facebook, then freely change their account's email address without re-verifying it, that new address can belong to someone else.

Walkthrough

  1. Sign up using Google/Facebook auth, so the account starts email-verified via the provider.
  2. Go to account settings and change the email to the victim's real address — check whether this requires a confirmation click on the new address.
  3. If not, the victim later tries to sign up with their own email, gets "already registered", resets the password — but the attacker's social login is still linked and still works.

Impact

Full account takeover that survives the victim's own password reset, because the attacker's login method (OAuth) was never removed.

Invariant: Changing the email on an account must require proving ownership of the new address before it takes effect.

Fix

Send a confirmation link to the new email and only swap it once that link is clicked; re-verify linked OAuth identities on email change.

OAuth CSRF account linking Auth

Declining

Modern OAuth libraries enforce `state` by default now; still worth checking on custom-built linking flows, especially older integrations.

The redirect that links a social account to an existing session is itself just a request — if it has no anti-CSRF `state` parameter, it can be triggered on a victim's behalf.

Walkthrough

  1. Start linking a social account (Google/Facebook) on your own account and intercept the request in Burp.
  2. Check whether a `state` parameter is present and actually validated on return.
  3. If missing, use Burp's "generate CSRF PoC" on the linking callback, then get a logged-in victim to open it.
  4. If it succeeds, your social account is now linked to the victim's account — log out, log back in via that provider, and you're in their account.

Impact

Account takeover with no password or OTP needed at all — just one click from the victim.

Invariant: The OAuth callback must be bound to the session that initiated it via an unguessable, single-use `state` value.

Fix

Generate and verify a random `state` parameter for every OAuth flow.

Delete account without re-authentication Auth

Still common

Still frequently missing — re-auth on destructive actions is often added for payments but forgotten for account deletion.

Account deletion is one of the most destructive actions a user can take, so it should require fresh proof it's really them — not just an active session.

Walkthrough

  1. Log in, go to account settings, find the delete/deactivate option.
  2. Trigger the deletion and watch whether it asks for the password (or an OTP) before completing.

Impact

A hijacked or left-open session (shared computer, stolen cookie) lets an attacker permanently destroy the account with one click.

Invariant: Irreversible actions must re-confirm identity at the moment they're taken, not rely on session state alone.

Fix

Require password or OTP re-entry immediately before executing account deletion.

Chapter 2 — Authentication & Login

Once an account exists, the login form becomes the front door, and this chapter is about every way a door can be propped open: no throttling on guesses, a lockout that's trivially sidestepped, or a second factor that can be told it already succeeded. The common thread is that the client should never be the one deciding whether a login attempt was correct.

Chapter invariant: A login attempt must be rate-limited per account and per IP, and success or failure must be decided entirely server-side — never by trusting a flag the client can flip.

No rate limit on login Logic

Still common

Among the most consistently reported and paid bugs across every major bounty program, year after year.

Without a cap on failed attempts, the login form is just an open door to password guessing.

Walkthrough

  1. Submit a login with a correct email and a wrong password; capture the POST request.
  2. Send it to Burp Intruder with a payload position on the password field, and a wordlist (simple list) of candidate passwords.
  3. Set 15-20 threads and run the attack.
  4. Sort by response length or status — the correct password usually produces a distinctly different response.

Impact

Credential stuffing / brute force leads directly to account takeover at scale.

Invariant: Repeated failed logins against the same account or from the same IP must trigger a slowdown or lockout.

Fix

Add progressive delays, IP-based throttling, and account lockout with a sane unlock mechanism.

Account lockout bypass via network change Logic

Still common

IP-scoped lockout remains a common implementation shortcut, so this bypass keeps working.

If lockout is tracked by IP address rather than by account, switching networks resets the attacker's attempt budget while the account-level brute force keeps going.

Walkthrough

  1. Enter wrong passwords until the account locks and the "try again later" message appears.
  2. Switch to a different network/IP (mobile hotspot, VPN).
  3. Try the correct password again — if it works, lockout was IP-scoped, not account-scoped.

Impact

Brute force becomes trivially distributable — rotate IPs, keep guessing.

Invariant: Lockout state must travel with the account, independent of which IP the attempt came from.

Fix

Track failed attempts per account (and per IP) rather than per IP alone; consider a growing cooldown.

2FA bypass via response manipulation Auth

Still common

Still extremely common on custom-built 2FA flows (vs. using a mature auth provider) — this is close to a first-pass check on any 2FA implementation.

If the client decides whether the OTP was correct — by reading a true/false field in the server's response — that field can simply be edited in transit.

Walkthrough

  1. Enter any six-digit code at the 2FA prompt and intercept the response in Burp (not the request — the response).
  2. Flip the relevant field from false to true, or error to success.
  3. Forward the modified response and see whether you're redirected past the 2FA step.

Impact

Full bypass of the second factor with no knowledge of the real code at all.

Invariant: Whether a code was correct must be a server-side decision enforced before issuing a session — never a value the client reads and acts on.

Fix

Issue the authenticated session only after server-side OTP validation; never return a simple pass/fail the client interprets.

2FA bypass via SSO misconfiguration Auth

Still common

Grows more relevant as apps add more login methods; keeping 2FA policy consistent across all of them is routinely missed.

If a social-login path was wired up without inheriting the same 2FA requirement as the password login, it becomes the easier door in.

Walkthrough

  1. Link a social account that has no 2FA requirement of its own.
  2. Log out, then log back in exclusively through that social provider.
  3. Check whether the app's own 2FA prompt is skipped entirely.

Impact

The 2FA protection on the account is only as strong as its weakest login path.

Invariant: Every authentication path into an account must enforce the same second-factor policy.

Fix

Require the app's own 2FA step regardless of which identity provider authenticated the user.

Server-side plaintext credential exposure Data

Declining

Rarer with modern SPA front-ends that don't server-render auth state into the page, but still appears on server-rendered legacy stacks.

Occasionally a page meant to collect the 2FA code still has the user's email/password embedded in its page source, left over from how the page was built.

Walkthrough

  1. Enable 2FA on an account, log out, then log back in with valid credentials to reach the 2FA interstitial page.
  2. View page source (or inspect network responses) and search for the email/password you just typed.

Impact

Anyone with access to that page's source (proxy logs, browser extensions, shared screen) recovers plaintext credentials.

Invariant: Credentials must never be echoed back into any page or response beyond the single auth request that needed them.

Fix

Strip credentials from any server-rendered page state after the auth check completes.

Privilege escalation via JWT role tampering AccessControl

Still common

As JWT-based auth has become the default for APIs and SPAs, trusting an unverified claim for authorization is a mistake that keeps recurring.

If the server trusts whatever role claim is inside a JWT without verifying its signature server-side, the role is just a string the client can rewrite.

Walkthrough

  1. Log in, intercept the response containing your JWT, and decode it at jwt.io.
  2. Edit the role claim from something like "user" to "admin".
  3. Re-sign/replace the token in your request (or simply resend it if the server doesn't check the signature) and load an admin-only page.

Impact

Full vertical privilege escalation — admin dashboards, user management, data exports.

Invariant: Authorization decisions must come from a signature-verified token checked server-side, never from an unverified claim.

Fix

Always verify JWT signatures server-side with a secret/key the client never has access to.

The same response-tampering idea as 2FA bypass, applied specifically to a reset flow's OTP check.

Chapter 3 — Session & Token Handling

A session is the thing standing between "logged in" and "logged out" for every request that follows. This chapter covers all the ways that boundary gets blurry: tokens that outlive the logout button, cookies that leak to pages they were never meant to reach, and pages that can be framed to steal a click meant for something else entirely.

Chapter invariant: A session token must be killed the moment the user logs out or changes their password, must never be readable by a page or script the user didn't intend to trust, and must never appear in plaintext in a URL, cache, or referrer.

Failure to invalidate session on logout Session

Still common

Still frequently found, especially in apps using stateless tokens with no server-side revocation list.

Logout should revoke the session server-side. Sometimes it only clears the client-side cookie, leaving the underlying session token still valid if it's replayed.

Walkthrough

  1. Log into the same account in two tabs of the same browser.
  2. Click logout in Tab A.
  3. In Tab B, without refreshing first, edit some profile data and save.
  4. Refresh Tab B and check whether the edit actually went through — if it did, Tab B's session was never killed server-side.

Impact

A stolen or captured session token remains usable long after the legitimate user thinks they've logged out.

Invariant: Logout must revoke the session on the server, not just clear a cookie on the client.

Fix

Invalidate the session record server-side on logout, not merely the client cookie.

Failure to invalidate session on password change Session

Still common

Same as above — a very common gap between 'password changed' and 'every other session killed'.

The same issue, triggered differently: when a password changes, every *other* active session for that account should die too.

Walkthrough

  1. Log into the same account from two different browsers.
  2. In Browser 1, change the password.
  3. In Browser 2 (still on the old session), try editing and saving profile data.
  4. If it saves successfully, the old session is still trusted even though the password that created it is gone.

Impact

An attacker who already has a foothold (stolen session) survives the legitimate user's attempt to lock them out by changing the password.

Invariant: Changing the password must invalidate every other active session for that account.

Fix

On password change, revoke all existing session tokens except the one that just performed the change.

Session fixation / cookie replay Session

Declining

Modern session libraries regenerate the session ID on login by default; still found in custom session handling.

If a session cookie, once exported, can simply be imported into a different browser and used to log in, the session is not bound to anything about the original device or login event.

Walkthrough

  1. Log into an account and use a cookie-editor extension to export all cookies.
  2. Log out.
  3. Open a fresh browser profile, go to the login page, and import the exported cookie instead of entering credentials.
  4. Refresh — if you're logged in, the exported cookie alone was sufficient.

Impact

Anyone who captures a session cookie (XSS, shared device, packet capture) gets durable account access without ever needing the password.

Invariant: A session must become unusable the moment it's logged out of, regardless of how the cookie itself is later replayed.

Fix

Rotate/invalidate session identifiers on logout; consider binding sessions to device fingerprint signals.

Missing Secure / HttpOnly on the session cookie Session

Declining

Most frameworks set both by default now — this has become a 'check it anyway, don't expect to find it' item on well-built targets, but still common on legacy or custom cookie handling.

Secure means the cookie is only ever sent over HTTPS; HttpOnly means client-side JavaScript can't read it. Missing either widens how the cookie can leak.

Walkthrough

  1. Export the site's cookies with a cookie-editor extension.
  2. Identify the one carrying the session.
  3. Check its flags for Secure and HttpOnly.

Impact

Without Secure, the token can leak over an accidental plain-HTTP request; without HttpOnly, any XSS on the site can read and exfiltrate it directly.

Invariant: A session cookie should be unreachable from JavaScript and unsendable over an unencrypted connection.

Fix

Set both Secure and HttpOnly (and SameSite) on every session cookie.

Token or credentials exposed in the URL Data

Declining

Modern SPA routing and OAuth implicit-flow deprecation have pushed tokens out of URLs in most new builds; still found on older server-rendered flows.

Putting a session token or password in a URL means it ends up in browser history, server access logs, and any Referer header sent from that page.

Walkthrough

  1. Log in and watch the URL bar for a token appended after redirect.
  2. Change your password and check the resulting URL (and browser history) for the old or new password in plaintext.

Impact

Anyone with access to browser history or server logs — including a shared computer or a misconfigured analytics tool — recovers the credential.

Invariant: Sensitive values belong in the request body or an encrypted cookie, never in the URL.

Fix

Move tokens out of query strings and into POST bodies or secure cookies.

Cleartext token transmission over HTTP Session

Declining

HSTS adoption and forced-HTTPS hosting have made this rarer, but still worth a quick check, especially on self-hosted or older infrastructure.

If a token is accepted over plain HTTP as readily as over HTTPS, it isn't really protected by TLS at all — anyone on the network path can read it in transit.

Walkthrough

  1. Capture a valid session token over HTTPS.
  2. Replay the exact same request over http:// instead.
  3. If the server accepts it, the token isn't bound to the secure channel it was issued on.

Impact

A man-in-the-middle on public wifi can lift the token straight off the wire.

Invariant: Session tokens must only be accepted over an encrypted connection.

Fix

Enforce HSTS and reject session cookies/tokens presented over plain HTTP.

Token leaked via Referer header to a third party Session

Still common

Still common precisely because it's easy to miss — a page can look perfectly secure and still leak via an embedded ad or widget's outbound request.

If a page containing a sensitive token in its URL also has outbound third-party links (ads, widgets, social buttons), clicking them sends that full URL — token included — as the Referer.

Walkthrough

  1. Open a reset-password link that puts the token in the URL.
  2. Click any third-party link present on that page.
  3. Inspect the outbound request's Referer header for the leaked token.

Impact

Any third party embedded on that page (and anyone logging their own access logs) can harvest live reset tokens.

Invariant: A page holding a sensitive token in its URL should not load third-party resources, or should strip the Referer.

Fix

Set a Referrer-Policy (e.g. no-referrer or same-origin) on pages carrying sensitive tokens, and avoid putting tokens in URLs at all.

Token leaked directly in a server response Session

Still common

A recurring API design mistake, especially as more reset/verify flows move to JSON APIs consumed by mobile apps.

Occasionally a reset/verification endpoint returns the token in its own JSON response body or headers — not just via the email channel, but to anyone who can call the endpoint.

Walkthrough

  1. Trigger a password reset and intercept the request/response in Burp.
  2. Inspect the full response body and headers, not just what renders on the page.
  3. Check whether the token meant only for the email is also sitting in the API response.

Impact

Anyone who can trigger a reset for a victim's email can read their reset token directly, no email access needed.

Invariant: A token meant for one delivery channel (email) should never also be exposed on another (the API response).

Fix

Strip sensitive tokens from any response not specifically meant to carry them.

Improper Cache-Control on sensitive pages Data

Declining

Modern frameworks and CDNs default to safer caching for authenticated routes, but still a real finding on custom or server-rendered legacy pages.

If a page showing account details isn't marked no-store, the browser (or a shared proxy) may cache it — so it reappears even after logout.

Walkthrough

  1. Log in and open a sensitive page (account/profile/settings).
  2. Click logout.
  3. Press the browser's Back button.
  4. Check whether the sensitive data is still visible, served from cache rather than a fresh (and now unauthorized) request.

Impact

On a shared or public computer, the next person to press Back sees the previous user's private data.

Invariant: Pages containing sensitive data must tell the browser never to cache them.

Fix

Send Cache-Control: no-store, no-cache on every authenticated, sensitive response.

Clickjacking on sensitive actions UI

Declining

Browsers now ship reasonable CSP/X-Frame-Options defaults in many frameworks, and the SameSite cookie default has blunted some clickjacking chains — but plenty of targets still don't set the header explicitly, so it's still worth testing.

Without a frame-blocking header, a page can be loaded inside an invisible iframe on an attacker's site and tricked into receiving clicks the user thinks are going somewhere else.

Walkthrough

  1. Copy the URL of a sensitive page (ideally one with a one-click destructive action, like delete-account or disable-2FA).
  2. Build a minimal HTML file that iframes that URL, with a decoy button/image layered on top using CSS.
  3. Open the file while logged in and confirm the target page loads inside the frame rather than refusing to.

Impact

An attacker can trick a logged-in user into unknowingly deleting their account, disabling 2FA, or performing any other framed action.

Invariant: A page that performs a sensitive action should refuse to render inside anyone else's frame.

Fix

Send X-Frame-Options: DENY (or a CSP frame-ancestors directive) on any page that triggers a sensitive state change.

Chapter 4 — The Password Reset Flow

If there's one flow worth mastering above all others, it's this one — a single broken link in the reset chain is usually one hop away from a full account takeover, and it tends to involve several different classes of bug stacked on the same feature: token design, header trust, and injection all show up here.

Chapter invariant: A reset token must be single-use, short-lived, unguessable, and permanently bound to the one email address it was issued for.

Reset token not invalidated after use Auth

Still common

Still a routine finding — 'used' state tracking on reset tokens is an easy thing to leave out.

A reset link that keeps working after the password has already been changed means the "used" state of the token was never actually tracked.

Walkthrough

  1. Request a password reset and open the emailed link.
  2. Use it once to successfully change the password.
  3. Reuse the exact same link to change the password a second and third time.
  4. If it keeps working, the token never expires on use.

Impact

Anyone who ever intercepted that reset link (shared inbox, email forwarding, archived message) retains indefinite password-reset power.

Invariant: A reset token must be marked used — and rejected — the instant it successfully changes a password.

Fix

Invalidate the token server-side immediately after a successful reset, and expire it after a short time window regardless.

Weak reset token design / sent over HTTP Auth

Declining

Most frameworks now generate tokens with a CSPRNG by default; still worth checking on custom-built reset flows.

Tokens that are short, sequential, timestamp-derived, or sent over an unencrypted link are all effectively guessable or interceptable.

Walkthrough

  1. Trigger a reset and copy the link straight from the email.
  2. Confirm it's HTTPS, not HTTP.
  3. Request several more resets back-to-back and compare the tokens for any visible pattern (incrementing numbers, obvious timestamps).

Impact

A predictable or interceptable token lets an attacker reset any account's password without ever touching the victim's inbox.

Invariant: A reset token must be cryptographically random, long enough to resist guessing, and always delivered over an encrypted channel.

Fix

Generate tokens with a secure random source, and never allow the reset flow to fall back to HTTP.

Host header poisoning on the reset link Injection

Still common

Grew, if anything, more relevant as more apps deploy behind multiple reverse proxies/CDNs that pass through client-supplied Host headers unchecked.

If the server builds the reset link using whatever Host header the request claims, an attacker can make the emailed link point at their own domain instead.

Walkthrough

  1. Trigger a forgot-password request and intercept it in Burp Repeater.
  2. Change the Host header (or add X-Forwarded-Host) to a domain you control.
  3. Send the request — if it returns 200 and the reset email actually goes out, check whether the link inside now points to your domain.

Impact

The victim clicks what looks like a normal reset email, lands on the attacker's lookalike page, and hands over their new password or the token itself.

Invariant: A link embedded in an email must be built from a trusted, server-configured domain — never from a client-supplied header.

Fix

Hardcode the canonical domain used to build reset links; never derive it from the Host header.

CRLF injection via a reflected parameter Injection

Declining

Most modern HTTP libraries now reject CR/LF characters in header values outright; still found on older frameworks or hand-built header logic.

If user input flows unsanitized into a response header (common on redirect/reset-adjacent endpoints), injecting a carriage-return/line-feed sequence lets you add your own headers — including a Set-Cookie.

Walkthrough

  1. Find a parameter that influences a response header, often on a redirect tied to the reset or login flow.
  2. Inject %0D%0ASet-Cookie: mycookie=myvalue into it.
  3. Check whether the response actually contains your injected Set-Cookie header, confirming the lack of sanitization.

Impact

Ranges from response-splitting and cache poisoning to session fixation and reflected XSS, depending on what else the header injection enables.

Invariant: User input must never be placed into a response header without stripping CR/LF characters.

Fix

Sanitize or reject CR/LF sequences in any input that flows into a header.

Weak cryptography in token generation Crypto

Declining

CSPRNG use is now the default in virtually every mainstream framework; still relevant on custom/legacy token generators.

Sometimes the "randomness" behind a reset token is actually a weak hash of predictable inputs (timestamp, user ID, a static secret) rather than true randomness.

Walkthrough

  1. Request several reset tokens in quick succession for a test account.
  2. Line them up and look for any pattern — shared prefixes, incrementing segments, something that correlates with time.

Impact

A pattern in token generation turns "guess a token" from infeasible to merely difficult — or trivial, depending on how weak it is.

Invariant: Token generation must use a cryptographically secure random source with no derivable relationship to user or time data.

Fix

Use a CSPRNG for token generation; never derive tokens from predictable fields.

Chapter 5 — Access Control & Business Logic

Every bug so far has been about what one user can do. This chapter is about what happens the moment two accounts exist — because access control bugs are invisible to someone testing with only their own login. Always work with two accounts, and always ask the same question for every feature: what stops User A from doing this to User B?

Chapter invariant: User A must never read, modify, or trigger an action on User B's data purely by changing an ID, role, or request path — authorization must be checked on every single request, not inferred from having a valid session.

IDOR on a user or object ID AccessControl

Still common

Consistently the single most-found access-control bug class across both web and mobile apps, now and for years running.

Insecure Direct Object Reference: the server trusts whichever ID you send it, without checking that the ID actually belongs to the requester.

Walkthrough

  1. Create two accounts; log into each in a separate browser.
  2. In Account A, find a request that references an object by ID — a phone number update, an invoice, an order.
  3. Capture the ID Account A uses, then substitute Account B's ID into the same request while authenticated as Account A.
  4. If the response returns or modifies Account B's data, authorization was never actually checked — just the ID.

Impact

Direct, scalable access to any other user's private data, simply by iterating IDs.

Invariant: Every request touching an object must verify the authenticated user actually owns (or is permitted to touch) that object.

Fix

Check object ownership server-side on every read/write, independent of what ID the client supplied.

Horizontal privilege escalation via identifier swap AccessControl

Still common

Still extremely common, and GraphQL/REST APIs exposing opaque-looking (but not actually unguessable) IDs keep this class alive.

The same underlying bug as IDOR, usually found through a slightly different path — copying an identifier (often a GUID) exposed somewhere public and reusing it in a sensitive action.

Walkthrough

  1. With two accounts open in two browsers, find a place where User A can see User B's GUID/ID (a public listing, shared workspace).
  2. Take an action that should be scoped to your own account (e.g. a password reset) but include the copied GUID.
  3. Check whether the action actually applies to the victim account instead of your own.

Impact

Same as IDOR — unauthorized access to, or modification of, another user's account or data.

Invariant: An identifier found in one context (a public page) must not silently grant privileges in another (a sensitive action).

Fix

Scope every sensitive action to the authenticated session's own user record, never to an ID taken from the request.

Vertical privilege escalation on privileged actions AccessControl

Still common

As products ship more role tiers (free/pro/admin/enterprise), the number of places this check can be missed keeps growing, not shrinking.

Beyond the JWT-role trick from Chapter 2, every privileged action — settings, data exports, admin-only pages — deserves its own check, since role enforcement is sometimes inconsistent across endpoints.

Walkthrough

  1. For each distinct privileged feature (not just login), repeat the role-tampering and endpoint-access tests.
  2. Try hitting admin-looking endpoints directly by URL while logged in as a normal user.
  3. Look especially at features added later — consistency tends to erode as an app grows.

Impact

Full admin capability on individual endpoints even where the main login flow was hardened.

Invariant: Authorization must be enforced per-endpoint, not assumed from a single successful role check elsewhere.

Fix

Centralize authorization checks (middleware/guard) so no individual endpoint can forget to apply them.

Logical flaw — racing an unverified account to lock out the victim Logic

Still common

Business-logic flaws like this one are genuinely harder to automate away than injection bugs, so they remain a strong source of findings.

Some chains don't fit a CWE cleanly; they're about the order operations happen in. This one exploits the gap between "email entered" and "email confirmed."

Walkthrough

  1. Create an account using the victim's real (but unconfirmed) email address.
  2. Before the victim confirms anything, enable 2FA on that account using your own phone/authenticator.
  3. The victim later finds the email already "registered," resets the password through the normal flow — but still can't get past your 2FA.

Impact

The legitimate owner is locked out of ever claiming the account tied to their own email.

Invariant: An unconfirmed account should not be allowed to configure security features (like 2FA) that could lock out the real owner.

Fix

Require email confirmation before allowing security-relevant changes such as enabling 2FA.

Content spoofing via a reflected parameter Injection

Declining

Most bounty programs now rate this low/informative unless it's chained into something with real impact, since output encoding defaults have made it less exploitable.

If a URL parameter (often an `error=` message) is reflected back into the page unescaped, you can make the site itself display attacker-chosen text.

Walkthrough

  1. Find a URL that reflects a parameter into visible page content — error/status messages are the usual suspects.
  2. Change the parameter's value to an attacker-controlled message (e.g. a fake "your account was compromised, call this number" string).
  3. Load the URL and confirm the text renders as part of the legitimate page.

Impact

A link that looks exactly like the real site, displaying text an attacker fully controls — effective for phishing.

Invariant: Any value reflected into the page must be HTML-escaped first.

Fix

Escape all reflected parameters before rendering them into the page.

CSRF on state-changing actions CSRF

Declining

Chrome's SameSite=Lax-by-default (since 2020) blocks the classic cross-site form-post version for most cookie-based apps; still very relevant for API/mobile clients, non-browser consumers, and GET-based state changes.

If a form that changes something important (email, password, PIN, profile data) doesn't check for a per-session anti-CSRF token, any page on the internet can submit it on the victim's behalf while they're logged in.

Walkthrough

  1. Pick a sensitive form — email change, PIN change, profile update — and capture the request while performing it normally.
  2. Use Burp's "generate CSRF PoC" to build a standalone HTML page that replays the exact request.
  3. Open that PoC in a browser where the victim session is active (or send it to a test victim) and see if the action executes.

Impact

Email/PIN/password changes, fund transfers, or any sensitive action — fired without the victim ever intending it.

Invariant: A state-changing request must include a token unique to the session that only the legitimate page could have embedded.

Fix

Require a per-session anti-CSRF token on every state-changing request, and set SameSite on cookies as defense in depth.

Chapter 6 — File Upload & Media

Only relevant where the target actually accepts uploads, but worth its own chapter because an upload field is really three different trust boundaries stacked together: what the file contains, what metadata rides along with it, and what happens when the server tries to process or re-serve it.

Chapter invariant: Anything a user uploads must be stripped of sensitive metadata, scanned before it's trusted, and inert (never executed) when it's later served back.

EXIF geolocation not stripped Privacy

Declining

Most major platforms (social apps, cloud photo services) now strip EXIF on upload by default; still common on smaller or custom-built apps that just store the raw file.

Photos from phones often carry embedded GPS coordinates and device info in their EXIF metadata. If the server re-serves an uploaded image as-is, that metadata travels with it.

Walkthrough

  1. Upload a photo that still has its original EXIF data (most phone camera photos do, pulled straight from the camera roll).
  2. Download the image back from the application (or find where it's served publicly).
  3. Run it through a metadata viewer like jimpl.com.
  4. Check whether GPS coordinates or device info are still present.

Impact

Exposes a user's precise location history and device fingerprint to anyone who can view their uploaded images.

Invariant: Any image accepted from a user must have identifying metadata stripped before it's stored or served.

Fix

Strip EXIF data server-side on upload, before the file is persisted.

No secure integrity check on uploads/downloads Infra

Still common

Still frequently missing, especially as more products add 'attach a file' features without AV scanning in the pipeline.

If a server accepts and later re-serves executable file types with no scanning, it becomes a free distribution channel for malware.

Walkthrough

  1. Upload a non-image executable type (.exe, .php, or a packaged shell) wherever file upload is accepted.
  2. If accepted, try downloading it back and check whether it's served as-is, still executable.
  3. This is a finding at "upload accepted," don't actually run anything malicious to prove it further.

Impact

The platform becomes a trusted-looking host for malware distributed under its own domain.

Invariant: Uploaded files must be scanned (AV/content inspection) and their executable types restricted before being accepted.

Fix

Validate file type by content (not just extension), scan on upload, and serve uploads with a non-executable content-disposition.

Stored XSS via file upload Injection

Still common

SVG upload handling in particular is still a reliable source of findings — many teams remember to sanitize text input but forget uploaded files can carry script too.

Some file types — notably SVG, and sometimes HTML — can contain embedded script. If the app renders the uploaded file inline rather than treating it as an opaque binary, that script runs in the victim's browser.

Walkthrough

  1. Find an upload field whose output is later rendered inline (profile pictures, document previews).
  2. Upload an SVG or HTML file containing a script payload.
  3. View the page where the upload is rendered and check whether the payload executes.

Impact

Persistent XSS against anyone who views the page containing the uploaded file — session theft, action-on-behalf-of.

Invariant: Uploaded content that can contain script must never be rendered inline without sanitization — or should be served from a separate, cookie-less origin.

Fix

Sanitize SVG/HTML uploads, or serve all user uploads from an isolated domain with no access to session cookies.

App-level DoS via an oversized or malicious upload Availability

Declining

Most cloud storage/CDN layers now impose size limits by default, but custom processing pipelines (resizing, thumbnailing, archive extraction) still get caught out.

An image with extreme pixel dimensions or a decompression bomb (a tiny file that expands to gigabytes) can exhaust server resources when the app tries to process it.

Walkthrough

  1. Find a file-upload field — a profile picture is the classic target.
  2. Upload either an image with enormous pixel dimensions, or a zip-bomb file (e.g. from bamsoftware.com/hacks/zipbomb) if archive extraction is supported.
  3. Save it and watch whether the server starts returning 500 errors or stops responding.
  4. Check from a different network/device whether the whole service is now affected, not just your own session.

Impact

A single malicious upload takes the application down for every user, not just the attacker.

Invariant: File processing must have strict, enforced bounds on size, dimensions, and extraction ratio before any work begins.

Fix

Validate and cap file size/dimensions before processing; set extraction limits for any archive handling.

Orphaned file still accessible after deletion AccessControl

Still common

A persistent class, especially with CDN-fronted storage where 'delete the DB row' and 'delete the object' are two different, easily desynced steps.

Deleting a profile picture or document from the account should also revoke access to its stored copy — a direct, unguessable-looking URL to the file isn't the same as actual access control.

Walkthrough

  1. Upload a file to the account and copy its direct URL.
  2. Delete the account or the specific file through the normal UI.
  3. Revisit the saved URL and check whether the file still loads.

Impact

Deleted "private" files remain permanently accessible to anyone who saved the link.

Invariant: Deleting a resource must actually remove or de-authorize access to its storage location, not just its reference in the UI.

Fix

Tie file access to a live authorization check, or actually delete/revoke the underlying object on deletion.

Chapter 7 — Classic Web Injection

The OWASP staples. These apply to nearly every input field on nearly every target, which is exactly why they're easy to under-test — it's tempting to try one payload on the obvious search box and move on. Treat every input, reflected parameter, and file-processing step as worth a pass.

Chapter invariant: User-controlled input must never be interpreted as code, markup, a database query, or a filesystem path by the server, the database, or another user's browser.

Reflected, Stored, and Blind XSS Injection

Still common

Still the single most-reported vulnerability class on HackerOne's own platform data, year after year — this is not a declining bug.

Cross-site scripting happens when user input is rendered back into a page without proper escaping, letting an attacker run arbitrary JavaScript in another user's browser.

Walkthrough

  1. Throw a baseline payload like ">
  2. For fields only an admin or support agent would later view (support tickets, display names), use a blind XSS payload tied to a service like XSS Hunter instead, since you won't see the result directly.
  3. Confirm execution: an alert box for reflected/stored, or a callback to your listener for blind.

Session hijacking, credential theft, or full account takeover of anyone who views the injected content — including, with blind XSS, internal staff.

Context-aware output encoding everywhere user input is rendered; a strict CSP as defense in depth.

Off-domain / DOM-based XSS Injection

Still common

Growing, if anything, as more logic moves client-side into JS frameworks with more DOM-writing surface area.

Some XSS never touches the server at all — a client-side redirect, a postMessage handler, or a URL fragment gets written straight into the DOM via an unsafe sink.

Walkthrough

  1. Look for client-side code that reads from location.hash, postMessage, or similar and writes it via innerHTML or document.write.
  2. Craft a URL/message that places a script payload into that sink.
  3. Confirm execution purely client-side, with nothing round-tripping through the server.

Impact

Same as standard XSS, but often missed by server-side filtering since the payload never actually reaches the server.

Invariant: Client-side code must treat URL/message data as untrusted and avoid unsafe DOM sinks.

Fix

Use safe DOM APIs (textContent, not innerHTML) for any untrusted client-side data.

SQL Injection (error-based) Injection

Declining

ORM adoption has pushed raw string-concatenated SQL out of most new code; still common in legacy codebases, raw-query escape hatches, and reporting/admin tooling.

If user input is concatenated directly into a SQL query, carefully crafted input can change the query's structure entirely.

Walkthrough

  1. Append a single or double quote to a numeric or string parameter (e.g. ?id=1') and watch for a database error or a change in page behavior.
  2. Balance the query using -- or --+ to comment out the rest of the original statement.
  3. Find the number of columns with ORDER BY N, incrementing N until the page breaks.
  4. Use UNION SELECT with that many columns to pull data into the page, then target @@version or version() to confirm the DB engine.

Impact

Full read (and often write) access to the underlying database — the most consequential class in this chapter.

Invariant: User input must never be concatenated into a query string; it belongs in a parameterized placeholder.

Fix

Use parameterized queries / prepared statements exclusively; least-privilege the DB account the app uses.

SSRF — Server-Side Request Forgery Injection

Still common

One of the fastest-growing high-value classes, especially as webhook/URL-fetch features (PDF export, link previews, avatar-from-url) become standard product features.

When a server-side feature fetches a URL on the user's behalf (webhooks, "avatar from URL", PDF generation), an attacker can redirect that fetch toward internal infrastructure instead.

Walkthrough

  1. Find any field that takes a URL and causes the server to fetch it.
  2. Point it at a listener you control (an ngrok tunnel works well).
  3. Confirm the callback arrives — this proves the server is making the request, not the browser.
  4. From there, try internal/metadata addresses (e.g. 169.254.169.254, internal hostnames) instead of your own listener.

Impact

Access to internal services, cloud metadata endpoints (sometimes yielding cloud credentials), and systems never meant to be internet-reachable.

Invariant: A server-side fetch triggered by user input must be restricted to an allowlist of legitimate external destinations.

Fix

Allowlist destinations for server-side fetches; block internal/link-local address ranges outright.

SSTI — Server-Side Template Injection Injection

Declining

Less common than it was, as more apps move server-side rendering off user-facing input paths, but still a real finding where free-text fields reach a template engine.

If user input is passed into a template engine rather than just being displayed as data, template syntax in that input gets evaluated.

Walkthrough

  1. Try a basic arithmetic payload like {{7*7}} (or ${7*7} depending on the engine) in free-text input fields.
  2. If the rendered page shows 49 instead of the literal text, the template engine is evaluating your input.
  3. From there, template-specific payloads can often escalate to reading files or executing commands.

Impact

Ranges from information disclosure up to full remote code execution, depending on the template engine.

Invariant: User input must be passed to a template as data, never concatenated into the template string itself.

Fix

Never build template strings from user input; pass user data only as template variables.

XXE — XML External Entity injection Injection

Declining

Most mainstream XML libraries disabled external entity resolution by default years ago (post ~2013-2017); still relevant on older Java/.NET stacks or libraries explicitly reconfigured to allow DTDs.

If an XML parser is configured to resolve external entities, a malicious XML document can make the server fetch local files or make outbound requests.

Walkthrough

  1. Find any endpoint accepting XML input.
  2. Submit a document with a DOCTYPE declaring an external entity pointing at a local file (e.g. file:///etc/passwd).
  3. Check whether the entity resolves and its content appears in the response.

Impact

Local file disclosure, and sometimes SSRF or denial of service via entity expansion.

Invariant: XML parsers must have external entity resolution disabled by default.

Fix

Disable DTD processing / external entity resolution in the XML parser configuration.

LFI / RFI / Path Traversal Injection

Still common

LFI/path traversal remains common; true RFI (remote URL inclusion) is rarer today since most languages disabled remote stream wrappers by default.

When a filename or include parameter is built from user input without sanitization, relative path sequences can escape the intended directory.

Walkthrough

  1. Find a parameter that references a file (e.g. ?file=image.jpg).
  2. Try a traversal payload like ../../../../../../etc/passwd in place of the expected filename.
  3. If the file's contents come back, local inclusion is confirmed; if the parameter instead accepts a full remote URL and fetches it, that's remote file inclusion.

Impact

Disclosure of sensitive server files (configs, credentials) and, with RFI, potential remote code execution.

Invariant: A filename parameter must be validated against an allowlist, never used directly to build a filesystem path.

Fix

Map user input to a fixed allowlist of files/paths server-side; never pass it straight to the filesystem API.

OS command injection Injection

Still common

Still shows up wherever a feature shells out to an external binary (image/video processing, PDF generation, network tools) — a small but consistently present surface.

Fields that plausibly shell out to a system command (image conversion, network diagnostics, export tooling) can sometimes have their input used unsanitized in that command.

Walkthrough

  1. Identify a feature that's likely implemented by shelling out (convert tools, ping-style utilities, export pipelines).
  2. Append a command separator and a harmless command, e.g. ; id or | whoami.
  3. Check the response for command output, or use a time-delay payload (; sleep 10) and measure response time if output isn't reflected.

Impact

Remote code execution on the server — as severe as it gets.

Invariant: User input must never be passed to a shell; use language-native APIs instead of invoking external commands with concatenated input.

Fix

Avoid shelling out with user input entirely; if unavoidable, use strict allowlisting and parameterized invocation (never string concatenation).

Open redirect Injection

Declining

Still found very often, but most bounty programs now pay little or nothing for it standalone — value comes from chaining it into OAuth state theft or phishing with another bug.

A `next=`/`redirect=`/`url=` parameter that's trusted without validation lets an attacker send users to an external, malicious destination through a link that still starts with the real domain.

Walkthrough

  1. Find a parameter controlling post-action redirection — often on login (?next=).
  2. Set it to an external address, e.g. //evil.com.
  3. Complete the action (e.g. log in) and confirm you land on the external domain.

Impact

Convincing phishing (the link starts with the real, trusted domain) and can chain into OAuth state theft.

Invariant: A redirect target must be validated against an allowlist of paths/domains before being used.

Fix

Only allow redirects to known-good, relative paths — never to arbitrary external URLs.

    Mostly historical

    Chapter 8 — Mobile (Android) Specifics

    Only relevant when an APK is explicitly in scope. Mobile apps add a layer that web apps don't have: the OS itself, and everything it exposes to other apps and to the device owner — clipboard, screenshots, and local storage.

    Chapter invariant: The app must not leave secrets or sensitive UI exposed to the OS layer — the clipboard, the screenshot/recording system, or unencrypted local files.

    Clipboard exposes sensitive data Mobile

    Declining

    Android has restricted background clipboard access since Android 10, narrowing this; still relevant for apps targeting older API levels or using legacy input types.

    If copy/paste isn't disabled on sensitive fields, whatever's typed there sits in the system clipboard, readable by any app with clipboard access.

    Walkthrough

    1. Open the app and enter something into a sensitive field (password, card number).
    2. Try copying it out and pasting into a notes app.
    3. On a rooted/debug device, Drozer's post.capture.clipboard module can also pull clipboard contents directly.

    Impact

    Any other app with clipboard-read permission (not uncommon) can silently capture sensitive user input.

    Invariant: Sensitive input fields should not allow their contents to be copied to the system clipboard.

    Fix

    Disable copy on password/sensitive fields using the platform's input-type flags.

    Screenshot / screen-recording enabled on sensitive screens Mobile

    Declining

    FLAG_SECURE is now a standard checklist item for fintech/banking apps specifically; still frequently missing on apps outside that space.

    Android's FLAG_SECURE prevents a given screen from appearing in screenshots, the app-switcher preview, or screen recordings. Sensitive screens should set it.

    Walkthrough

    1. Navigate to a sensitive screen (payment details, 2FA code entry).
    2. Trigger the OS screenshot and check if it actually captures the content.
    3. Also check the recent-apps switcher preview for the same screen.

    Impact

    Sensitive data lingers in the photo gallery, is visible to anyone glancing at the app switcher, or gets captured by screen-recording malware.

    Invariant: Any screen displaying sensitive data must block screenshots and recording at the OS level.

    Fix

    Set FLAG_SECURE on activities/windows that display sensitive information.

    Wi-Fi SSID and password stored in plaintext Mobile

    Mostly historical

    Niche even when it was common — mostly relevant to older IoT/smart-home setup apps; most current frameworks push credential storage into the Android Keystore by default.

    Some apps that handle local network setup persist the Wi-Fi credentials they used to a config file, unencrypted, inside their app data directory.

    Walkthrough

    1. Connect the app to a local Wi-Fi network through its own setup flow.
    2. On a rooted/debug device, browse to the app's data directory and look in any wifi-related subfolder for a config file (e.g. wpa_supplicant.conf).
    3. Open it and check whether the SSID and password are stored in plaintext.

    Impact

    Anyone with local device/file access recovers the user's home or office Wi-Fi password.

    Invariant: Credentials the app stores locally must be encrypted at rest, never written in plaintext.

    Fix

    Encrypt any locally persisted credentials using the platform keystore rather than a flat config file.

    Chapter 9 — Modern API & Auth Attacks (Post-2023) New — post-2023

    The original notes predate the shift to API-first, token-heavy architectures — GraphQL endpoints, microservices talking over signed tokens, everything running on cloud infrastructure with its own metadata service. These six classes are where the bug bounty payouts have been concentrating since 2023-2024: they're not replacements for the classics, they're the classics' API-native cousins.

    Chapter invariant: A token, a schema, or a cloud identity must only grant exactly the access it was issued for — never more, just because the client asked a cleverer way, asked twice at once, or asked from inside the server's own network.

    JWT algorithm confusion (RS256 → HS256 downgrade) Auth

    Rising

    One of the clearer post-2023 growth areas as JWT-based auth became the default for API-first and microservice architectures.

    Some JWT libraries pick the verification algorithm from the token's own header instead of hardcoding what the server expects. If a server normally verifies tokens with an RSA public key (RS256) but will also accept HS256, an attacker can sign a forged token with HMAC using that same public key as the "secret" — because the public key is, by definition, public.

    Walkthrough

    1. Find the server's public signing key, often published at a JWKS endpoint like /.well-known/jwks.json.
    2. Reconstruct it as a PEM (watch for formatting quirks — SPKI vs PKCS#1, trailing newline).
    3. Forge a new JWT with the header algorithm changed from RS256 to HS256, claiming whatever identity/role you want.
    4. Sign it using HMAC-SHA256 with the PEM-formatted public key as the secret.
    5. Submit the forged token and see whether the server verifies it successfully.

    Impact

    Full authentication bypass — forge a token for any user, including an admin, with no credentials at all.

    Invariant: The verification algorithm must be fixed by the server, never read from the token being verified.

    Fix

    Hardcode the expected algorithm at every verification call site; never derive it from the token's own alg header.

    JWT none-algorithm & kid-based tricks Auth

    Declining

    Mainstream JWT libraries patched alg:none acceptance years ago; still occasionally found in custom/older JWT parsing code, especially the kid-header injection variant.

    Related forgery techniques: some implementations accept alg:"none" and skip signature checking entirely; others trust a client-supplied kid (key ID) header enough to let it be abused for path traversal or SQL injection when the server uses it to look up the verification key.

    Walkthrough

    1. Decode a valid token and change the header's alg to "none", then strip the signature entirely — submit and see if it's accepted.
    2. If the token carries a kid header, try path-traversal values (e.g. ../../../dev/null) or injection payloads in it, since some servers use that value directly in a file or database lookup to find the verification key.

    Impact

    Either a trivial unsigned forged token, or a way to trick the server into verifying against a key of the attacker's choosing.

    Invariant: An unsigned token must be rejected outright, and any value used to select a verification key must be validated against a strict allowlist.

    Fix

    Explicitly reject alg:none; validate kid against a known-good key registry rather than using it as a raw lookup path.

    GraphQL introspection & schema disclosure Logic

    Rising

    GraphQL adoption keeps growing, and introspection being left on in production remains a very common default-config mistake.

    GraphQL APIs are typically self-documenting: an introspection query asks the API to describe its entire schema. This is meant for development tools, but if left enabled in production it hands an attacker the complete map of every query, mutation, and field the API supports.

    Walkthrough

    1. POST the standard introspection query (requesting __schema) to the GraphQL endpoint, commonly at /graphql or /api/graphql.
    2. If it's blocked, try a field-suggestion probe instead — sending a deliberately misspelled field name; many servers helpfully respond with "Did you mean: realFieldName?", leaking schema structure even with introspection off.
    3. Map the returned schema for anything that looks sensitive — admin mutations, internal-only fields, fields with no obvious UI exposure.

    Impact

    A complete attacker's map of the API's capabilities, including hidden/internal mutations never exposed in the app's own UI.

    Invariant: A production GraphQL endpoint should not expose its full schema to unauthenticated or unauthorized callers.

    Fix

    Disable introspection in production; apply authorization before schema details are ever returned.

    GraphQL BOLA/IDOR and batching abuse AccessControl

    Rising

    As more products move from REST to GraphQL, this is becoming the dominant access-control bug class on those targets specifically.

    The same object-level authorization and rate-limit problems from Chapters 2 and 5 reappear inside GraphQL — but GraphQL's own features (global object IDs, query aliasing, batched requests) give them a sharper edge.

    Walkthrough

    1. Test every query/mutation that takes an object ID (often a base64 "global ID" encoding type+ID) by swapping in a second account's ID — the same IDOR test as Chapter 5, just through GraphQL.
    2. Use query aliasing to bundle many variations of the same query/mutation into a single HTTP request (e.g. aliasing a login or OTP-check mutation 50 times with different credentials/codes in one POST).
    3. Send the batched request and check whether per-request rate limiting was bypassed because it was all technically "one request."

    Impact

    Cross-tenant data access via BOLA, or a full rate-limit/brute-force bypass via alias batching that a simple per-request limiter never sees.

    Invariant: Authorization must be checked per object inside a GraphQL resolver, and rate limiting must count each aliased operation inside a batch, not just the outer HTTP request.

    Fix

    Enforce object-level authorization in every resolver; count GraphQL operations (not HTTP requests) against rate limits, and cap query depth/cost.

    Mass assignment / Broken Object Property Level Authorization AccessControl

    Rising

    Explicitly called out in the current OWASP API Security Top 10 (BOPLA) — a strong, well-documented growth area in API-first products.

    Frameworks that auto-bind JSON request bodies straight onto a database model are convenient — and dangerous, if the model has fields (role, is_admin, price, package_name) the client was never supposed to set directly. Sending those extra fields in a normal-looking update request can silently grant them.

    Walkthrough

    1. Find an endpoint that updates an object — a profile, an order, a subscription — and capture the normal request body.
    2. Diff the response/API docs against the request: look for fields present in the model but absent from the normal form (role, is_admin, price, verified, package_name, created_by).
    3. Add one of those fields to the request body with an attacker-favorable value and submit.
    4. Check whether the field actually changed, confirming the server bound it without an allowlist.

    Impact

    Ranges from self-granted premium features to full privilege escalation to admin, simply by adding a field the client was never shown.

    Invariant: Only fields the API explicitly intends to be client-writable should ever be bound from a request body.

    Fix

    Use an explicit allowlist (DTO/serializer) for writable fields instead of binding the whole request body onto the model.

    SSRF chained to cloud metadata credential theft Injection

    Rising

    AWS pushing IMDSv2 as default on new instances has reduced the easiest version of this, but GCP/Azure metadata services and older unpatched AWS instances keep this chain very much alive.

    When an application server hosted on AWS/GCP/Azure has an SSRF bug, the highest-value target to point it at isn't an internal admin panel — it's the cloud provider's own instance metadata service, which hands out the server's live IAM credentials to anything that can reach it from inside the instance.

    Walkthrough

    1. Confirm basic SSRF first (Chapter 7) by making the server fetch a URL you control.
    2. Redirect the same vulnerable parameter at the metadata service instead: 169.254.169.254 (AWS/GCP/Azure all use this link-local address, with provider-specific paths).
    3. On AWS, check whether IMDSv1 is in use (a simple GET works) versus IMDSv2 (requires a PUT to fetch a session token first, via header X-aws-ec2-metadata-token) — IMDSv1 is directly abusable through a classic SSRF with no extra steps.
    4. If metadata is reachable, pull the IAM role name, then the role's temporary credentials endpoint, to retrieve AccessKeyId/SecretAccessKey/SessionToken.

    Impact

    The SSRF stops being a web-app bug and becomes full access to whatever AWS/cloud resources that server's IAM role can reach — S3 buckets, other internal services, sometimes the whole account.

    Invariant: A server's own cloud credentials must never be reachable through a request path the application itself exposes to user input.

    Fix

    Migrate to IMDSv2 (which requires a custom header SSRF typically can't forge) and block outbound requests to 169.254.169.254 at the application/network layer regardless.

    Race conditions / TOCTOU on single-use or limited actions Logic

    Rising

    Tooling (Turbo Intruder, single-packet attack techniques) has made race conditions dramatically easier to find reliably, which shows directly in rising report volume.

    Any action that's supposed to happen "only once" or "only while a balance/limit allows it" is enforced by a check followed by a use — and if those two steps aren't atomic, firing many identical requests at the exact same instant can make several of them pass the check before any of them records its own use.

    Walkthrough

    1. Find an action gated by a one-time or limited resource: redeeming a promo/referral code, confirming an email change, submitting a flag/vote once, applying a discount, withdrawing a balance.
    2. Capture the request in Burp and send it to Repeater (or Turbo Intruder for true parallel firing).
    3. Fire 10-20 identical copies of the request at once, as close to simultaneously as possible.
    4. Check whether the limited action succeeded more than once — multiple redemptions, a doubled withdrawal, two different emails both confirmed.

    Impact

    Duplicated payouts, multiple redemptions of a single-use code, or bypassing a security check (like OTP attempt limits) by racing past the counter before it increments.

    Invariant: A check-then-use sequence on a limited resource must be atomic — the check and the use happen as one indivisible database operation.

    Fix

    Use database-level locking or atomic compare-and-swap operations for any check-then-use logic on limited resources.
